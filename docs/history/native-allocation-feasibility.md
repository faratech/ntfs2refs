# Native ReFS allocation as a metadata generator

Research date: 2026-10-23. This is an architectural hypothesis, not an implemented conversion path. No disk controls, image writes, or VM changes were performed for this investigation. The separate Windows 11 Pro 26300.9457 native Dev Drive data control succeeded; native extent placement and metadata transplantation remain unmeasured. See [lab results](lab-results.md).

**Finding:** native APIs could reduce the amount of ReFS metadata-writing code, but the reviewed Microsoft contracts do not establish a complete way to adopt caller-selected NTFS payload locations. `SetFileValidData` is supported on ReFS; arbitrary ReFS placement and a bounded, payload-free metadata transplant remain separate unproven requirements. Do not label `FSCTL_MOVE_FILE` universally unsupported on ReFS: the API page does not say that, and current `defrag` documentation includes ReFS among eligible filesystems. [MOVE_FILE](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_move_file), [defrag](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/defrag)

## What the contracts establish

| Interface | Documented behavior | Consequence for this hypothesis |
| --- | --- | --- |
| `FSCTL_MOVE_FILE` / `MOVE_FILE_DATA` | Relocates existing file clusters within the same volume. Caller supplies starting file VCN, destination LCN and cluster count. The contract includes no metadata-only/no-copy switch. ReFS-specific acceptance and placement constraints are not stated. | Candidate for a disposable-volume placement experiment; not proof of direct allocation or no payload I/O. A free-space bitmap is only a point-in-time observation. [Control](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_move_file), [input](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-move_file_data) |
| `SetFileValidData` | Explicit ReFS support. Advances valid-data length without writing the file's data or filling allocated clusters with zeros. Requires `GENERIC_WRITE` and `SE_MANAGE_VOLUME_NAME` when initially opening; excludes sparse, compressed and transacted files. | Can avoid initialization of an already allocated ordinary file. It has no address selector and does not promise that preceding allocation/move operations avoid writes. Restrict access to unwritten contents. Sparse-source handling needs another path. [API](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfilevaliddata) |
| `FILE_ALLOCATION_INFO` | Supplies allocation size in bytes, with no destination address field. | Requests capacity, not a chosen LCN. [Structure](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_allocation_info) |
| ReFS block clone | Remaps existing allocated file regions, maintains references and isolates later writes. Both files must already be on the same ReFS volume; offsets are cluster aligned and integrity settings must match. | Does not import a raw NTFS extent or select an arbitrary disk address. It may help only after data is represented by an existing ReFS file. [Microsoft description](https://learn.microsoft.com/en-us/windows/win32/fileio/block-cloning) |
| `FSCTL_REARRANGE_FILE` / `FSCTL_SHUFFLE_FILE` | Rearranges or adds/removes allocations within files. Documented as kernel-only; parameters describe file offsets, not arbitrary physical targets. | Outside this project's user-mode, stock-driver path; not an alternative allocator for it. [Rearrange](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ni-ntifs-fsctl_rearrange_file), [shuffle documentation source](https://github.com/MicrosoftDocs/windows-driver-docs-ddi/blob/staging/wdk-ddi-src/content/ntifs/ni-ntifs-fsctl_shuffle_file.md) |

The SDK's declaration of an FSCTL constant establishes an interface identifier, not support by each filesystem. No public allocate-at-physical-address or import-arbitrary-extents ReFS contract was found in this bounded review. This is an unresolved capability, not proof that every possible native implementation is impossible. [Microsoft SDK header](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/winioctl.h)

## Retrieval pointers are not automatically physical sectors

`FSCTL_GET_RETRIEVAL_POINTERS` explicitly supports ReFS and returns nonresident file VCN-to-LCN mappings; resident content has no extent location. Microsoft defines VCNs relative to a file and LCNs relative to a point within the volume, and expressly disclaims a guaranteed mapping to physical disk sectors. The retrieval-pointer-base query supplies a sector offset used to derive volume-relative extent offsets; cluster and sector units must first be reconciled. [Retrieval pointers](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_get_retrieval_pointers), [address definitions](https://learn.microsoft.com/en-us/windows/win32/fileio/clusters-and-extents), [retrieval base](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_get_retrieval_pointer_base)

Therefore keep API LCN, independently decoded ReFS metadata addresses, raw-partition byte offset, guest-disk offset and host VHDX storage offset distinct. Equal numbers do not establish equal address spaces. For the intended basic-disk profile, resolve the native mapping against unique known payload bytes in an offline raw capture. Do not apply an assumed `LCN * cluster_size` translation to source payload or metadata. The refcount query adds ownership evidence, not a placement guarantee. [Refcount operation](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/85810832-f7c5-42eb-a54d-2328ac8bb861)

## Why identical geometry is insufficient

The proposed disposable image would need native file mappings at precisely the desired raw offsets, then a complete metadata image whose file contents are supplied by the retained NTFS payload. The following are engineering proof obligations, not documented guarantees:

- **Placement:** native metadata or reserved regions can occupy requested locations. No reviewed API promises control of all metadata placement, collision relocation, or every fragmented requested run.
- **Scratch and I/O:** moving an uninitialized file before advancing valid length might avoid copying data, but that optimization is undocumented. A dynamic/sparse backing image does not by itself bound allocated scratch or write volume. Measure both, including flush/remount activity.
- **Complete metadata:** file extents alone do not identify every required allocator, reference-count, checkpoint, log, checksum and discovery block. A raw diff cannot reliably classify data versus metadata. Preserving a complete native-produced filesystem state would still require a verified extraction and transplantation method.
- **Payload semantics:** original NTFS uninitialized tails, resident data, sparse regions, alternate streams and shared identities need deliberate treatment. A native placeholder's logical zeros are not evidence that its raw allocation is safe to substitute with old bytes.
- **Content-dependent metadata:** enabled integrity streams record checksums in metadata and validate reads against them. Placeholder-derived checksums cannot certify different retained payload. An integrity-disabled initial profile would still need explicit policy and native validation; metadata integrity remains relevant. [Integrity streams](https://learn.microsoft.com/en-us/windows-server/storage/refs/integrity-streams)
- **Commit and recovery:** copying a subset of native metadata is not a documented filesystem migration transaction. Collision planning, bounded journaling, crash recovery and first-writable-mount handoff remain required. OS boot work is deferred.

## Smallest useful future experiment

These are proposed measurements only, on a separately identified disposable ReFS data disk after the native format control succeeds:

1. First use read-only retrieval/base/refcount observations for a small file with unique cluster contents. Compare them with a clean offline raw capture to establish address units and actual payload locations.
2. If that agrees, separately test one documented move to a currently free candidate LCN. Record exact inputs, error/status, returned mappings, content hashes and offline destination bytes. Distinguish unsupported-operation errors from alignment, privilege, occupied-range and parameter failures.
3. Separately test ordinary allocation plus valid-data advancement, then the proposed operation order with relocation. Bound file size and attempts; measure physical scratch growth and changed raw ranges. Success of `SetFileValidData` alone cannot establish a write-free sequence.
4. Require stable results after clean dismount/remount before considering any metadata extraction design. A successful tiny placement probe establishes only that exact profile and operation; it does not qualify extent-preserving conversion or OS boot.

Until those observations exist, retain native allocation as an experimental alternative alongside the independently verified reader/writer research. No conversion gate is satisfied by these API descriptions.

## Shadow metadata generated inside the converter's Windows environment

The proposed shadow is a standalone file-backed virtual disk created and attached **inside the guest during lab work**, using the same native Windows APIs available on a physical machine. Microsoft explicitly describes VHD APIs as independent of other virtualization technologies; Windows 11 also exposes creation and attachment through Disk Management. Rust can call `VirtDisk.dll` (`CreateVirtualDisk`, `AttachVirtualDisk`, `GetVirtualDiskPhysicalPath`, `DetachVirtualDisk`); DiskPart is a possible control implementation. Hyper-V, host-side VHD attachment/conversion, and checkpoints are laboratory infrastructure, never dependencies of the converter. [Native VHD platform](https://learn.microsoft.com/en-us/windows/win32/vstor/about-vhd), [Windows VHD management](https://learn.microsoft.com/en-us/windows-server/storage/disk-management/manage-virtual-hard-disks)

Create an empty dynamic VHDX with no `SourcePath` or `ParentPath`: those parameters can populate data or introduce backing dependencies. Match the intended partition length, offset, logical/physical sector sizes and ReFS cluster size, then verify what the attached device actually reports. Give the scratch disk its own identities and bind its returned device path to the creation handle; never select it by a guessed disk number. Preserve the original target GPT identities and copy only planned partition-relative ranges, not the scratch GPT. Identical geometry still does not prove that every ReFS address or identifier is transferable. [Creation parameters](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/ns-virtdisk-create_virtual_disk_parameters), [attached device identity](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-getvirtualdiskphysicalpath)

**Only the scratch volume is natively formatted. The original NTFS partition is never a formatter or discard target.** Generate its intended namespace and ordinary file allocations on the shadow, attempt placement while their valid-data length is zero, then advance valid length after placement. This is a hypothesis for obtaining metadata without payload-size I/O; the preceding API contracts do not guarantee it. A shadow placeholder's bytes must never overwrite retained NTFS payload. Keep the measured Dev Drive creation profile explicit, including per-file integrity settings; ordinary ReFS and Dev Drive are not interchangeable qualifications.

The first implementation profile should require bounded external scratch and recovery storage. Keeping the backing file on the NTFS conversion target creates a dependency on that filesystem while the virtual disk is attached. Exclusive locking fails while files remain open. On-volume staging would therefore require a separate, proven detach/export protocol before committing and is not part of this initial design. [Volume locking](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_lock_volume)

### Why the allocation bitmap is only a candidate copy-set source

`FSCTL_GET_VOLUME_BITMAP` describes occupied/free clusters at one instant; it is not documented as a complete filesystem serialization or metadata-backup interface. Microsoft also documents `STARTING_LCN_INPUT_BUFFER_EX` and `GET_VOLUME_BITMAP_FLAG_MASK_METADATA = 1`, described as including metadata. Test ordinary input, extended input with flags zero, and extended input with that flag separately. Preserve ABI size, status, returned start, reported bitmap size and actual bytes. The extended structure's WDK documentation does not establish user-mode acceptance or exact ReFS bootstrap/reserved-region coverage. [Bitmap contract](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_get_volume_bitmap), [extended input](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-starting_lcn_input_buffer_ex)

Let `B` be the occupied set in an independently resolved address space and `P` the verified ordinary payload clusters that will be retained on the target. `B minus P` is a **candidate**, not an accepted metadata copy set. A complete candidate also needs every mandatory discovery/backup region outside bitmap coverage, and all metadata reachable from the required roots, checkpoints and recovery state. A file retrieval map does not classify those structures. Do not subtract unknown streams, uninitialized tails, resident contents, shared allocations or any range whose role/address has not been established. Do not reinterpret a huge reported bitmap as physical coverage by silently truncating it to volume length. [Bitmap layout and rounding](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-volume_bitmap_buffer)

Independently decoded metadata must close over its references: every required referenced range must resolve into the proposed copied set or a deliberately retained payload range. Include zero-valued required fields, redundant copies and mount-discovery structures; a scan for nonzero bytes or known signatures cannot establish completeness. VHDX backing-file allocated ranges and block-allocation tables describe the container, not the ReFS metadata/data distinction. `FSCTL_QUERY_ALLOCATED_RANGES` likewise identifies possible nonzero file regions, not their meaning. [Allocated-range contract](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_query_allocated_ranges)

### Bounds, frozen state and falsifiable gates

Dynamic virtual capacity is not an actual-storage cap. `MaximumSize` is virtual capacity; full physical allocation reserves the entire virtual disk, while a dynamic image can grow as native operations touch more backing blocks. Record virtual size, provider-reported physical size, backing-file length/allocated storage, total external-volume consumption and cumulative I/O separately. `GetVirtualDiskInformation` and `GetCompressedFileSizeW` expose different useful measurements. Account for container blocks, logs, evidence and the recovery journal, not just copied ReFS bytes. [Creation flag](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/ne-virtdisk-create_virtual_disk_flag), [virtual/physical size](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/ns-virtdisk-get_virtual_disk_info), [allocated file storage](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getcompressedfilesizew)

A bounded external scratch volume can enforce a storage ceiling; polling a file length cannot prevent an in-flight operation from exceeding a soft threshold. Reserve recovery capacity before any target write, finish and validate all native shadow generation first, and reject an oversized result. Disk-full during shadow generation must leave the target untouched. A native operation that copies or zeroes every placeholder cluster defeats the desired I/O/space bound even when its final mappings look correct.

The following gates are sequential; failure stops advancement rather than enabling a fallback formatter on NTFS:

1. **Platform and ownership:** create, attach, identify, cleanly detach and reopen a small scratch image using guest-side Windows APIs only. Then test the required large virtual geometry within the declared actual-storage budget. The current Dev Drive control requires its measured size/RAM profile; a smaller source partition does not inherit that qualification.
2. **Placement and address translation:** compare requested and returned mappings against independent raw payload markers across multiple locations/runs. A single matching extent does not establish a volume-wide linear map. Test initialized relocation separately from zero-VDL placement; prove the latter's payload-write and scratch-growth bounds before using it to generate a source-sized namespace.
3. **Bitmap coverage:** compare ordinary and extended bitmap results with all independently decoded mandatory metadata and reserved/discovery regions, and with known payload ownership. Bound every query, validate rounded starts, and record partial/out-of-domain observations as incomplete. Inclusion of some metadata is not proof of full coverage.
4. **Frozen final state:** complete native operations, flush, close handles and cleanly detach. Reattach read-only and reacquire observations against that exact immutable state; explicitly test whether the native queries work there. Read-only attachment is documented, but successful ReFS query/replay behavior must be observed. If it cannot be established, stop extraction. Bind all ranges and evidence to the final image hash. [Attachment flags](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/ne-virtdisk-attach_virtual_disk_flag), [detach requirements](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-detachvirtualdisk)
5. **Invalidation:** any allocation, file move, valid-length change, flush that changes the image, writable remount, replay, integrity change, shrink/expand, or component/profile change invalidates prior bitmap/extent/copy-set evidence. Re-resolve addresses and regenerate the plan. Never mix mappings from the original native corpus with those of a newly formatted shadow.
6. **Reconstruction before conversion:** on a separate disposable test target, retain uniquely patterned payload at planned offsets and reconstruct only the proposed metadata set. Existing NTFS structures and nonzero canaries in omitted ranges must be represented in the test; a freshly zero-filled target can conceal missing zero initialization. Require native read-only recognition, complete file/stream hashes and semantics, then isolated writable remount, new allocations and reboot checks. Every referenced pointer/checksum must pass the independent reader. Successful mounting alone cannot show that free-space ownership or later allocation is correct. This remains a reconstruction test, not an NTFS conversion result.
7. **Original-partition commit:** only after the preceding gates pass, construct a collision plan against the original NTFS allocation map. Any metadata/payload overlap requires a bounded, journaled relocation and regenerated shadow mappings, or rejection. Journal each overwritten original range and the commit state before writing, preserve original partition identity, and verify retained payload offsets/hashes. Inject interruptions before writable ReFS handoff and demonstrate recovery without a VM checkpoint. Native generation does not supply that transaction protocol.

This approach could let the stock driver generate ReFS structures while the converter implements validated selection, placement, collision handling and recovery. Neither bitmap subtraction nor a sparse backing file removes those obligations. No shadow conversion path is qualified or implemented by this research; boot experiments remain deferred.
