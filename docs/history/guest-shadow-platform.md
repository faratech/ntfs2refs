# Guest-local native shadow platform

This prepares an independently formatted ReFS shadow inside Windows. The intended production mechanism uses the Windows Virtual Disk API and native Storage module, without Hyper-V APIs or host attachment. The current wrapper deliberately binds the disposable guest; Hyper-V supplies lab isolation/checkpoints only. This does not convert the source, copy its payload, or qualify metadata transplantation.

Proposed interface: `Prepare-GuestShadowPlatform.ps1 -RunId <32 lowercase hex> -JournalManifestPath <enrolled journal JSON>`.

1. Require the original guest OS, 8 GiB memory, unchanged Dev Drive policy, and exact journal UniqueId `600224806AAC261F021F249596F332FC`, empty serial, LUN2, 8 GiB, 512/4096 sectors, online/writable, RAW with zero partitions. Refuse occupied J: or S:. Never pass the source target to a mutating command.
2. Initialize only that blank journal as GPT. Create J: at 16 MiB, length `8 GiB - 32 MiB`, quick-format NTFS/4096, label `ntfs2refs-journal`.
3. Create protected ordinary directories `J:\ntfs2refs-shadow\<RunId>` and new `shadow.vhdx`. Reject existing files, reparse points, compression and EFS. Create an independent dynamic VHDX: 64 GiB virtual capacity, 2 MiB blocks, 512/4096 sectors, fresh GUID, zero flags, NULL ParentPath/SourcePath. Omit FULL_PHYSICAL_ALLOCATION; v2 access mask is zero. [CreateVirtualDisk](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-createvirtualdisk), [parameters](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/ns-virtdisk-create_virtual_disk_parameters).
4. Open with a v2 handle; verify VHD GUID, dynamic subtype3, capacity and geometry. Attach using `NO_DRIVE_LETTER | PERMANENT_LIFETIME` (0x6). Attachment survives handle close, not a guaranteed reboot attachment policy. Audit the current process token's assigned `SeManageVolumePrivilege`, enable it only around Attach, then restore and requery its exact previous attributes and close the token. Missing assignment or uncertain restoration stops preparation. This enables an existing privilege; it cannot add one or elevate the process. [Attach requirement](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-attachvirtualdisk), [AdjustTokenPrivileges](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-adjusttokenprivileges), [flags](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/ne-virtdisk-attach_virtual_disk_flag).
5. Bind `GetVirtualDiskPhysicalPath` to the sole new disk, distinct from all original disks. Require RAW/no partitions,64 GiB,512/4096. Initialize only that new disk, create S: at16 MiB/52 GiB, then native `Format-Volume -DevDrive -FileSystem ReFS -AllocationUnitSize 4096`. Record component provenance and native DevDrive/volume/ReFS queries. No fallback or policy changes. [Physical-path contract](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/nf-virtdisk-getvirtualdiskphysicalpath).
6. Return the attached shadow's backing path/VHD GUID, physical disk number/UniqueId/GPT GUID, partition GUID/offset/length, volume GUID, and native evidence. Requery backing size after creation and formatting. Journal8 GiB is the hard capacity boundary; enforce a 6 GiB post-stage ceiling on VHD physical size, file length and actual allocation, with at least 1280 MiB free (1 GiB journal plus 256 MiB reserve). This does not guarantee every native format will fit. [VHD size/subtype](https://learn.microsoft.com/en-us/windows/win32/api/virtdisk/ns-virtdisk-get_virtual_disk_info), [actual file allocation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getcompressedfilesizew).

Write mutation intent/stage evidence to unique C: output before each operation. The host bounds synchronous native calls; format jobs have a separate deadline. Transport/deadline uncertainty preserves the running branch. Returned failure preserves journal/VHDX/attachment. No automatic detach, deletion or retry. Root may cleanly shut down and checkpoint successful preparation; subsequent use needs identity-bound reattachment. No fixture payload is created by this platform helper.

Fresh collision/metadata coverage, address-translation invariants, undo-journal completeness, retained semantics and native remount require separate evidence before conversion.

VHD backing identity is native query14 (`virtualDiskId`), pinned to the creation request on every observation. Query2 (`identifier`) is preserved as separate content-generation evidence and may change when native initialization writes disk contents. Neither is the GPT disk GUID. See [the measured identity correction](shadow-identity.md).

After a clean reboot, `Restore-GuestShadowAttachment.ps1 -RunId <id> -ObservationId <new id> -PreparationEvidenceSha256 <hash> -NativeSourceSha256 <hash> -Mode Prepared|Excluded` reopens only the existing backing file. It binds the exact journal, initial three original disks and successful preparation before one privilege-scoped attachment. Prepared mode keeps the original writable VHD profile, restores S: only when unused, and verifies the stored volume GUID/ReFS identity. Excluded additionally requires `-ProtectionNativeSourceSha256 <hash>` and `-MountNativeSourceSha256 <hash>`; it opens/attaches the backing read-only, proves provider write protection, and explicitly establishes offline/read-only attributes on the new device. This follows the [measured protection diagnostic](shadow-readonly-attachment-diagnostic.md), without assuming shadow attribute persistence. Excluded requires the original target to remain offline/read-write, preserves its GPT/partition identity before/after, and hashes the entire shadow backing before/after within a 256 MiB lab bound. It never assigns S: or queries shadow filesystems. Both modes require the same physical disk3, stable VHD ID, GPT and partition identities. The single output remains `C:\ntfs2refs\shadow-attachment\<RunId>\<ObservationId>\attachment.json`, at most1 MiB, status `shadow-attachment-restored` or `failed-preserved`. Intent, native calls, privilege cleanup and unknown completion are retained. It never creates, formats, detaches or deletes the shadow; failures preserve the branch.

The implementation is `lab/guest/Prepare-GuestShadowPlatform.ps1` with `NativeShadowDisk.cs` and the unchanged `GuestLab.psm1`. The new shadow label is `n2r-retained-shadow`, coordinated with the separate retained-file fixture helper. Native v2 creation layout is 128 bytes on x64, with its union at offset8; open-v2 is28 bytes and attach-v1 is8 bytes. Tests check those layouts and exercise the lifecycle against an injected API without creating or attaching any VHD.

Output is `C:\ntfs2refs\shadow-platform\<RunId>\prepare.json` (schemaVersion1, kind `guest-local-shadow-platform`). Success status is `shadow-platform-prepared`; errors return `failed-preserved`. The record includes `shadow` (physicalPath, diskNumber, diskUniqueId, diskGuid, partitionGuid, partitionNumber, offset, length, logicalSectorSize, physicalSectorSize, letter, volumeGuid, filesystem and allocationUnitSize), journal enrollment/partition identity, VHD identifier and backing path, native query buffers as bounded hex, formatter/native component hashes, and allocation observations. Success also requires `attachmentRetained`, `handleCloseSucceeded`, `nativeOperationCompletionKnown` and `privilegeRestored` true. `manageVolumePrivilege` records assignment, original/enabled/restored attributes, API results and cleanup; `privilegeAdjustmentAttempted` reflects the actual attempt. `sourceTargetWriteRequestsIssued`, `payloadCopied`, `conversionQualified` and `bootQualified` stay false.

The export allowlist is `prepare.json` (at most1 MiB), plus optional `system`, `devdrive`, `volume`, and `refs` `.stdout`/`.stderr` files (at most64 KiB each): at most9 files/1.5 MiB total. Export complete failure evidence before choosing any recovery; timeout or transport interruption can leave an active operation even when the last durable record predates its completion. Native format has a180-second deadline; each fsutil process has a30-second exit deadline and5 seconds per redirected output stream. Process IDs and observed exits are retained. The orchestrator bounds the complete invocation. No process/format job is forcibly stopped.
