# ReFS implementation evidence for the native-shadow design

Research date: 2026-10-24. This review inspected the pinned repositories and source files below without importing, building or running their code. These are primary implementation/research sources, not a Microsoft on-disk compatibility specification. Repository support claims and author-reported corpus validation are distinguished from this project's native measurements.

**Finding:** none of the inspected projects supplies a reusable general ReFS writer. They are useful independent reader references. Creating a coherent ReFS filesystem through the native Windows driver remains the concrete metadata-generation path for our bounded shadow experiment; replacing that path would require substantially more than translating NTFS file records.

## Structural facts and disagreements that matter

**Metadata topology.** NTFS describes every file through MFT records, including resident data or mappings to external storage. ReFS readers instead bootstrap `SUPB` → `CHKP` → `MSB+` ministore B+ trees; container, object, allocator and other system tables participate. This is a different metadata graph, not a renamed MFT. Microsoft's documentation also confirms mandatory ReFS metadata checksums, optional file-data integrity and reference counts for block-cloned regions. Block cloning requires both files on the same ReFS volume, so it is not an NTFS extent-adoption API. [Microsoft MFT](https://learn.microsoft.com/en-us/windows/win32/fileio/master-file-table), [libfsrefs format topology](https://github.com/libyal/libfsrefs/blob/77e1b7ba68cf225ec888a61e9784fb9a93a0156f/documentation/Resilient%20File%20System%20%28ReFS%29.asciidoc), [integrity streams](https://learn.microsoft.com/en-us/windows-server/storage/refs/integrity-streams), [block cloning](https://learn.microsoft.com/en-us/windows-server/storage/refs/block-cloning).

**An on-disk virtual cluster is not automatically a device LCN.** `refsprogs` implements a bootstrap physical region followed by container mapping in `refs_node_logical_to_physical_block_number`. Its mapping-table indexing and cluster-size constants are implementation assumptions to test, not a universal formula. `forefst` uses actual container IDs and the candidate rule `cid = vlcn >> bit_length(CPC)`; the physical cluster is the mapped container base plus `vlcn & (CPC - 1)`. For its power-of-two profile, the skipped boundary bit must be zero. It documents 160-byte container values for the ordinary 4 KiB profile and 224-byte variants for 64 KiB/SHA-256. Physical bootstrap pages are a separate address class. [refsprogs code](https://github.com/unsound/refsprogs/blob/bd9036823aa3bf06de6dc30fecd669712c59c0e9/librefs/node.c#L1397-L1477), [forefst container reference](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/structures/container_table.md).

**Conversion consequence:** retain the distinction among file VCN, on-disk virtual cluster, native retrieval-pointer LCN, volume byte offset and physical-disk byte offset. Accepting one requires explicit translation and identity-bound raw-byte/hash agreement, not numerical equality with another. A formula observed for 3.4 does not qualify native 3.14. Our existing bounded [container reader](../../src/refs_containers.rs) and [virtual-root reader](../../src/refs_virtual_roots.rs) remain restricted to their measured profile.

**Checksums need exact algorithms and reference layouts.** The libfsrefs reference labels checksum type 2 CRC64-ECMA-182. The newer forefst reference and `refs_crc64` implementation identify reflected CRC64/NVME with polynomial `0x9a6c9329ac4bc9b5`, plus a ReFS stored-sentinel rule. These are incompatible algorithm descriptions. It also distinguishes padded 104-byte, compact 48-byte and SHA-256 72-byte page references. Treat this as a documented disagreement resolved by native corpus checks, not by selecting the newest prose. This project's [CRC64 implementation](../../src/refs_bootstrap.rs) already uses NVME and has a check-vector/sentinel test; it was not changed by this review. CRC agreement proves a local byte/reference consistency check, not complete filesystem health or transaction currency. [Older descriptor](https://github.com/libyal/libfsrefs/blob/77e1b7ba68cf225ec888a61e9784fb9a93a0156f/documentation/Resilient%20File%20System%20%28ReFS%29.asciidoc), [new checksum reference](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/concepts/checksum_architecture.md), [actual CRC code](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/forefst.py#L3372-L3518).

**Allocation is not one self-explanatory bitmap.** Forefst describes Medium, Container and Small allocator trees, variable bitmap rows and compact uniform-range rows. Its research explicitly leaves the address basis of Container/Small row ranges unresolved, despite identifying their metadata-page addressing. It reports overlapping tier management in newer formats, saturating counters and reservations outside simple free-space totals. Its container-flag meanings are labeled inference. These sources therefore do not establish that a union of decoded bits, or native volume-bitmap bits minus file extents, identifies every metadata/reserved byte required for transplantation. [Allocator reference](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/structures/allocators.md), [container flags](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/structures/container_table.md).

**Reader recovery behavior cannot authorize conversion.** `forefst.Translator.tr` returns the input address on an unmapped container after recording a miss. Its known-issues page also documents damaged superblock/checkpoint cases that can produce misleading displays or a passing verdict. Our admission path must stop on unresolved mapping, incomplete traversal, checksum failure or ambiguous checkpoint selection. A forensic recovery result can remain useful without meeting that stricter requirement. [Translator implementation](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/forefst.py#L898-L923), [published known issues](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/tools/forefst.md#known-issues-in-1131). Version alone is insufficient: the reference also describes upgraded volumes retaining older layouts. [Version evolution](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/concepts/version_evolution.md).

## Concrete next steps for our design

These are engineering conclusions, not additional externally established format facts:

1. Keep native shadow generation and guest-local operation. Let the signed native driver construct coherent namespace, security, allocation, references, checksums and checkpoint/log state. Keep whole-partition comparison and durable journal coverage until a **complete** metadata-only copy set is independently established; the allocator research does not establish that optimization.
2. Complete [bounded NTFS admission](../bounded-converter-next-step.md): allocated MFT records, all nonresident attributes, namespace indexes, source bitmap and ownership must reconcile. A successfully preserved fixture does not establish this for arbitrary files. System reservations and unsupported features need explicit rules rather than silent exclusion.
3. Extend independent read-only validation against hash-pinned native images: every reachable page's address class, table ID, bounds, checksum descriptor, checksum and traversal budget; container-map duplicates/gaps; exact retained extent translation and raw-byte agreement. Include malformed/ambiguous cases, and stop rather than taking reader recovery fallbacks.
4. Keep the native 3.14/4 KiB/checksum profile explicit. Add separate fixtures before admitting older upgraded layouts, SHA-256 or 64 KiB variants. Record Windows build, native formatter provenance and geometry alongside the VBR version.
5. A future direct Rust ReFS writer would need independently verified allocator/refcount updates, namespace/security semantics, checkpoint selection, log/recovery rules and crash tests. The inspected readers provide research leads, not that writer. No external implementation code was copied or introduced as a dependency by this review.
