# Proactive Windows conversion audit

The original Windows installation remains healthy NTFS. This audit qualified
the captured source metadata and the existing Rust trust-label restoration
mechanism on a disposable native ReFS volume. It does not establish that the
original installation has been converted or boots from ReFS.

## Problems found and corrected

| Problem | Correction | Actual evidence |
| --- | --- | --- |
| Nested `System Volume Information` directories were refused late. | Enroll the source root and ordinary empty immediate children with fresh native identities, metadata owners, and exact namespace checks. Existing file bounds and collision refusals remain. | The captured source's five directories and four files pass the constructor preflight. |
| The flat security oracle produced a different inherited API view. | Reproduce the original source parent hierarchy and restore directory security before file security. Do not mask inherited/protected flags. | All 541 native constructor kernel/API views match, including the previously failing case. |
| Combined time/attribute/reparse/type eligibility ran only during native completion. | Share the exact native predicate with early construction and the all-row diagnostic. | All 143,552 captured source objects pass with zero errors. |
| The security graph walker treated a native internal boundary row as an unsupported leaf form. | Permit only the observed final keyless internal row: 64 bytes, flag word 2, empty key, and a 48-byte authenticated child reference. Keep leaf checks unchanged. | Both checkpoint graphs plan successfully; native journaled application and strict post-mount readback pass. |

The whole-source metadata check completed in 36.146 seconds with a paid RAM
peak of 3,725,633,312 bytes under its existing 4,576,660,480-byte budget. It opens
the existing closed metadata, not the original source device.

## Native trust-label result

The exact release at `6f2381bcf9579e12934c0c3875bb1b5ed81a448d` used the existing
Rust writer and journal on the separately identified disposable ReFS disk.

- All 369 descriptor recipes matched exactly once in each checkpoint.
- The writer changed 78 clusters, totaling 319,488 bytes; its journal is 653,568 bytes.
- Actual native writer process 4084 exited successfully; durable handoff closed
  before the volume returned online.
- Independent readback matched the original stored and API security semantics
  for all 541 objects, including the parent contexts and all supported trust-label variants.
- All 160 deterministic file payloads matched. There were zero observer errors,
  and temporary process privileges were restored.
- The source disk was not opened by this experiment. Its original NTFS partition
  remains at offset 331,350,016 with length 66,236,448,768 bytes.

The oracle is security-focused: source timestamps, attributes, reparse payloads,
full Windows construction, original-disk boot, and restart recovery of a complete
Windows conversion are separate qualification steps. Matching security rows may
also restore identical placeholders from the older disposable test subtree;
the earlier receipts and corpus remain preserved.

Detailed hashes and custody paths are recorded in
`evidence/windows-native-trust-context-qualified-20261107.json`.

## Research that informed the corrections

- Microsoft's [MSIX chain of trust](https://devblogs.microsoft.com/insidemsix/msix-chain-of-trust/)
  explains why process-trust labels protect WindowsApps package content. Dropping
  the labels would change that protection.
- Microsoft's [automatic inheritance conversion](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-converttoautoinheritprivateobjectsecurity)
  documents parent-dependent inherited ACE and protection flags. It supports
  testing the actual parent context; it does not establish the internal
  implementation of `GetSecurityInfo`.
- The primary reverse-engineering [B+ tree row reference](https://github.com/xbqt/forefst/blob/main/docs/structures/btree_node.md)
  describes the row fields. The specific internal-row exception above is backed
  by captured Microsoft-generated bytes and subsequent native acceptance,
  rather than a generic interpretation of every reserved bit.
- Microsoft's [ReFS boot preview documentation](https://learn.microsoft.com/en-us/windows-server/storage/refs/refs-boot-windows-server-unattend)
  requires UEFI/GPT and a separate NTFS recovery partition for that Server
  preview. It is not a Windows 11 support contract. The read-only boot audit
  found matching selected ReFS service settings and EFI loader bytes between
  the original installation and the working control. No speculative registry,
  BCD, firmware, or Secure Boot changes were made.
