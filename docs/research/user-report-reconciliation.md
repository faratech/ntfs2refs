# Reconciliation of the supplied conversion research

Reviewed 2026-10-24 against the immutable repositories in [implementation evidence](refs-implementation-evidence.md) and the current local readers/journal. The report's opaque citation IDs are not resolvable source links here. The concrete sources below were independently inspected; agreement with research does not expand our native qualification or establish a general converter.

## Format claims: accepted scope and corrections

| Claim | Reconciliation and required boundary |
|---|---|
| SUPB is at LCN 30, with tail copies. | The pinned forefst reference describes three copies at `30`, `total_clusters - 2`, and `total_clusters - 3`. These are **volume-relative clusters**, not host-file offsets or the final two sectors. Each copy has its own self-LCN/checksum; they are not byte-identical. Accept these as candidate locations for the bounded profile, then validate geometry, signatures, identity, bounds and self-checksums. Our [bootstrap reader](../../src/refs_bootstrap.rs) does this only for 3.14/4 KiB. [Pinned SUPB reference](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/structures/supb.md). |
| The higher CHKP clock is sufficient to select the active filesystem. | **Insufficient.** The reference selects among checksum-valid candidates using the clock at `CHKP+0x60`; it describes invalid-newer fallback and an explicit equal-clock case. Header clock, structure, identity and root references also need validation. Its opening shorthand is weaker than its selection section. Our parser records both candidates and explicitly leaves `authoritative_checkpoint_selected=false`; a larger number does not change that. [Pinned CHKP selection](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/structures/chkp.md#checkpoint-selection-and-fallback). |
| Thirteen roots, with 7/8/12 physical and the others virtual. | This matches the documented modern profile and our candidate reader. Root indices do not authenticate contents: check each page's table identity, volume identity, descriptor and checksum. The container pair is the set `{0x0b,0x0c}` and may swap order. Direct/indirect root-list encoding and reference width must be decoded before following addresses. These are profile rules, not assumptions for every ReFS generation. [Pinned root table](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/structures/chkp.md#13-root-table-pointers), [local physical-root checks](../../src/refs_bootstrap.rs). |
| Container translation uses `CPC.bit_length()`. | Supported as the examined research formula: `cid = vlcn >> bit_length(CPC)` and `plcn = base[cid] + (vlcn & (CPC-1))`, with power-of-two CPC and the skipped boundary bit clear. Our [virtual-root reader](../../src/refs_virtual_roots.rs) admits only CPC 16384, shift 15, mask `0x3fff`, and bit 14 clear. Require the exact map, range and overflow checks; never use an unmapped-container identity fallback. `refsprogs` has its own cluster-size-dependent map indexing. Neither proves that an on-disk VLCN equals a native retrieval-pointer LCN. [forefst rule](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/structures/container_table.md#address-translation-vlcn-to-plcn), [refsprogs implementation](https://github.com/unsound/refsprogs/blob/bd9036823aa3bf06de6dc30fecd669712c59c0e9/librefs/node.c#L1397-L1477). |
| Allocator row `+0` is a physical range in every tier. | **Overstated.** The pinned reference establishes this interpretation for Medium rows in its measured corpus but explicitly leaves the Container/Small row address basis unresolved. Metadata-page addressing is a separate question. Rows may be compact rather than bitmap-bearing, counters may saturate, and tiers may overlap. This does not establish a complete metadata copy set or an ownership certificate. [Pinned allocator reference](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/structures/allocators.md#bitmap-row--variable-length). |
| Child-page checksums reside in parent references. | Correct for the examined tree-reference mechanism, but not a universal statement that every page is covered by a parent. SUPB/CHKP have self-descriptors. Width, algorithm, assembled page slots and coverage must match the profile. CRC64/NVME is the local measured candidate; the older libfsrefs document's ECMA label conflicts with it. A valid checksum alone establishes neither currentness nor semantic correctness. [Pinned checksum architecture](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/concepts/checksum_architecture.md), [local checksum code](../../src/refs_bootstrap.rs). |
| SecurityId can be constructed from a descriptor hash. | The reference describes low 32 bits as an NTFS-style SD hash and high 32 bits as collision generation, with a separate descriptor table. Its actual `_refs_sd_hash` performs `h = ROL32(h,3) + little_endian_dword`, modulo 2^32. This is not CRC32/CRC64 or a cryptographic identity. Hash equality cannot replace full descriptor comparison, collision handling and valid table insertion; generation/serialization must not be assumed portable. Our current shadow uses native security APIs, not a raw SecurityId writer. [Pinned security layout](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/structures/security_descriptors.md), [actual hash implementation](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/forefst.py#L8678-L8687). |

## Two different conversion contracts

The report's **direct-writer/free-space-staging** design can preserve a structurally valid old NTFS until cutover only if every earlier target write avoids all live NTFS state, including metadata, logs, backup structures and payload. It also needs complete allocation/ownership admission and exclusion of concurrent NTFS allocation. Fixed ReFS anchors may collide with live NTFS bytes; their location does not make them safe. Writing a VBR last is ordering, not proof of an atomic sector update, complete ReFS state, or recoverability after a torn write. These are requirements deduced from the proposed contract, not guarantees supplied by the reader research.

Our **whole-shadow/external-journal** protocol has a different intermediate-state guarantee. It compares complete frozen source/shadow partitions, preserves explicitly admitted source payload intervals, and journals every changed granule's old and replacement bytes. It may overwrite live NTFS metadata **before** replacing the first 4096-byte discovery region. Thus the surviving NTFS VBR does not imply a mountable NTFS filesystem. The original target must remain persistently offline across interruption/restart; independent journal/ticket identities and full-byte validation are recovery authority. [Actual write ordering](../../src/lab_reconstruct.rs), [journal contract](../lab-reconstruction-journal.md).

Native filesystem handoff is a separate boundary. A normal mount can perform recovery, repair or bookkeeping; a read-only application handle does not establish a write-protected disk. The SUPB research describes repair during mount, while Microsoft's disk API separately exposes persistent offline/read-only attributes. Our path therefore records durable handoff before the protected mount, detaches the shadow, and proves original-target disk read-only protection before bringing it online. Any nonzero handoff barrier closes this journal's apply/resume/rollback paths, including after observer failure. Restoring a lab VM checkpoint is not production rollback. [Mount-repair research](https://github.com/xbqt/forefst/blob/d4d5fd28942eb14ebe11d90f4eb9342f5e3d7b92/docs/structures/supb.md#self-descriptor), [Microsoft disk attributes](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-set_disk_attributes), [verification boundary](../native-retained-postconversion-verification.md).

## Accepted requirements for further work

- Production filesystem work remains guest-local Windows API work, portable to bare metal. Hyper-V provides isolation/checkpoints for the lab; it is not part of the conversion algorithm. The [shadow platform](../guest-shadow-platform.md) uses a guest-owned backing file and local Virtual Disk APIs, not a host-mounted target.
- Preserve source payload bytes only after complete admission, exact native mappings, address translation and raw hash agreement. Record any required relocation/copy explicitly. Matching one prepared fixture is not a general no-recopy result.
- Account separately for unchanged **target payload**, initialized **shadow payload**, formatter metadata, dynamic backing-file allocation, full-volume reads and external journal storage. A shadow pattern or native allocation may consume scratch even when the source payload is never copied into it. Do not equate a sparse virtual capacity with a proven physical-storage bound for arbitrary inputs.
- Keep the current writer and recovery contract explicit. A future direct ReFS writer with free-space staging is a separate implementation and proof obligation; the supplied report does not retroactively give our current protocol that intermediate NTFS-validity guarantee.

No code, qualification flag, VM state or runtime protocol was changed by this reconciliation.
